# Publishing Vacuon on winget

`winget install Vacuon` is the closest thing to a fix for the SmartScreen warning that does
not cost money. It does **not** make the warning disappear for someone who downloads the
`.exe` by hand and double-clicks it — that warning comes from the shell checking an unsigned
binary's reputation, and only a code-signing certificate silences it. What winget gives is a
second route that never passes through that dialog, plus a manifest that a Microsoft-run
repository reviewed.

## What gets submitted

`InstallerType: portable`. There is no installer, so winget stores the `.exe` and puts an
alias named `vacuon` in its links directory, which is already on `PATH`. `winget uninstall`
removes both.

Four files, all generated by `new-manifest.ps1` — never edited by hand, because three of them
repeat `PackageIdentifier` and `PackageVersion` and that is exactly the kind of duplication
that drifts:

| File | Holds |
|---|---|
| `Joedsonalves.Vacuon.yaml` | the version and which locale is the default |
| `Joedsonalves.Vacuon.installer.yaml` | architecture, URL, SHA256, minimum OS |
| `Joedsonalves.Vacuon.locale.en-US.yaml` | name, publisher, licence, description, tags |
| `Joedsonalves.Vacuon.locale.pt-BR.yaml` | the same in Portuguese |

## Releasing a version

The manifest can only be written **after** the release exists, because the SHA256 has to match
the published bytes.

```powershell
# 1. publish the release first, then generate against the exact file that was uploaded
.\new-manifest.ps1 -Version 0.3.1 -ExePath ..\..\artifacts\release\Vacuon-0.3.1-win-x64.exe
```

The script hashes the local file rather than taking a typed value. A wrong hash does not fail
here — it fails on every user's machine, because winget refuses a download that does not match.

The URL points at the asset **with the version in its name**. The
`releases/latest/download/...` link is right for the README, where a permanent link matters
more than precision; here it would be a bug, since the hash is fixed and what `latest` serves
is not.

## Testing the install before opening the PR

Needs an elevated terminal once, to let winget read a manifest off disk:

```powershell
winget settings --enable LocalManifestFiles
winget install --manifest .\0.3.1\
vacuon --version
winget uninstall Joedsonalves.Vacuon
```

## Opening the PR

`microsoft/winget-pkgs` expects the files under a path built from the identifier:

```
manifests/j/Joedsonalves/Vacuon/0.3.1/
```

```powershell
gh repo fork microsoft/winget-pkgs --clone --remote
# copy 0.3.1\ into manifests/j/Joedsonalves/Vacuon/0.3.1/ of the fork, then
gh pr create --repo microsoft/winget-pkgs --title "New package: Joedsonalves.Vacuon version 0.3.1"
```

Their CI validates the manifest, installs the package in a sandbox and runs it. Expect a bot
comment within minutes and a human review after that.

## What will be asked

- **The publisher must be the owner.** The package is served from `github.com/joedsonalves`,
  which matches the declared publisher.
- **The binary must not be flagged.** An unsigned self-contained .NET executable of 62 MB
  sometimes trips a heuristic. If that happens, submit the file at
  <https://www.microsoft.com/en-us/wdsi/filesubmission> and link the ticket in the PR.
- **`Tags` are capped at 16** and are matched literally by `winget search`.
